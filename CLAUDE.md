# Berth

Single-host, multi-user "Linux workstation in the browser". One machine runs many Docker containers, one per user. Each container has a terminal (ttyd) and a remote browser (neko + Chromium). A user logs in on a web page and sees their own terminal and browser. Idle containers are stopped, later removed; user data lives on a dedicated volume and is restored on the next login.

**Scope guard: no Kubernetes, no message queue, no microservices.** The whole system is one Go backend process + Traefik + Docker. Do not over-engineer; prefer the simplest thing that satisfies this document.

## Working agreement

- Work in the milestones below, **one at a time**. After each milestone: list what was built, how it was verified, and the decisions that need confirmation — then **stop and wait for the go-ahead**.
- All configuration is via environment variables; every variable is documented in `.env.example` (add new ones in the same change that introduces them).
- Core logic (state transitions, idle detection) has unit tests. The Docker client is always behind an interface (`internal/docker`) so it can be mocked.
- No heavy frontend UI kits (Tailwind or plain CSS only).
- Develop on the branch the session designates; never push elsewhere.
- Verify against the real stack, not just unit tests: Traefik and Docker behave in ways the docs do not make obvious (see "Verified facts"). Mutation-test security-relevant logic: a test that still passes when the check is deleted is not a test.

## Tech stack

- **Backend:** Go, `chi` router, `github.com/moby/moby/client` for Docker (the spec's `github.com/docker/docker/client` last released v28.5.2+incompatible and cannot be tidied on Go 1.24; the moby module is its maintained successor), SQLite via `modernc.org/sqlite` (pure Go, **no cgo**). SQL is isolated behind the `store.Store` interface so Postgres can come later.
- **Proxy:** Traefik v3 (`traefik:v3.7`; Docker Engine 29 needs >= 3.6.1) with the Docker provider for routes and the file provider (`traefik/dynamic.yml`) for the shared ForwardAuth middleware. The backend never proxies user traffic itself.
- **Frontend:** React + Vite + TypeScript. Terminal = xterm.js; browser view = neko's own web UI in an iframe.
- **User image:** `images/workspace/` — `ghcr.io/m1k1o/neko/chromium` (pinned, amd64/arm64) + ttyd, CLI tools, non-root `user` (uid 1000, home `/home/user`). `berth/workspace:latest` is only ever built locally, never pulled (the `berth/` Docker Hub namespace is not ours).
- **Deploy:** `docker-compose.yml` brings up Traefik + the backend and builds the workspace image. There is no frontend service: the backend image's Node stage (`Dockerfile`) builds `web/` and the Go stage embeds the result (`internal/webui`), so one process serves the app, the API and nothing else.

**Go version:** the spec says Go 1.22+. `go.mod` says `go 1.24` because that is the oldest Go the security-fixed `x/crypto` (>= v0.45.0), the moby client and a current SQLite (`modernc.org/sqlite` >= v1.46, bundling SQLite 3.51) support. The Dockerfile builds on a supported release (`golang:1.26-alpine`). Build with `GOTOOLCHAIN=local` and never let `go get @latest` raise the `go` directive unreviewed.

## Data model (SQLite)

```
users(id, username UNIQUE, password_hash, is_admin, created_at)
sessions(token_hash PK, ws_token_hash UNIQUE, user_id, created_at, expires_at)
workspaces(user_id PK -> users, container_id NULL, state, volume_name UNIQUE,
           mem_limit_mb DEFAULT 2048, cpu_limit DEFAULT 2.0,
           last_active_at, last_stopped_at, updated_at,
           udp_port_start NULL UNIQUE, udp_port_end NULL, neko_password NULL)
```

One workspace per user. `state` ∈ `offline | starting | running | stopped` (CHECK-constrained). `container_id` NULL means the container was removed and only the volume remains. The first registered user is admin (decided atomically in the INSERT). Timestamps are UTC text `YYYY-MM-DD HH:MM:SS`; **never bind a `time.Time` directly** (the driver stores its monotonic-clock string) — use the store's `fmtTime`.

Schema changes are versioned migrations (`PRAGMA user_version`, contiguous `NNNN_name.sql`, each applied atomically); never edit a shipped migration. The store refuses a database newer than the binary. SQLite cannot `ADD COLUMN ... UNIQUE` or `NOT NULL` without a default: add nullable columns, backfill, then `CREATE UNIQUE INDEX` (partial, `WHERE ... IS NOT NULL`). Transactions are `BEGIN IMMEDIATE` (`_txlock=immediate`), so read-then-write sequences are safe; table-rebuild migrations need `PRAGMA foreign_keys=OFF` outside the transaction.

**State changes are compare-and-swap:** `Store.TransitionWorkspace(userID, from[], to, opts...)` is one `UPDATE ... WHERE state IN (from)` that returns `ErrStateConflict` if someone else got there first. That is what makes a double-clicked "Power on" create exactly one container. Always derive `from` from `workspace.Sources(event)`, never hard-code it.

## Lifecycle state machine

```
offline ──"power on"──▶ starting ──container healthy──▶ running
running ──idle timeout (default 30 min) or user "power off"──▶ stopped   (docker stop, container kept)
stopped ──"power on"──▶ starting ──▶ running                              (docker start, seconds)
stopped ──idle again (default 7 days)──▶ offline                           (docker rm, volume kept)
any ──container vanished──▶ offline
```

`internal/workspace/state.go` is the pure state machine (`Event`, `Next`, `Sources`, `Observe`) and is exhaustively unit-tested. **Login does not power on**; the user presses "Power on" (`POST /api/workspace/start`). Start returns once the container is started; **readiness is the image's Docker healthcheck** — `GET /api/workspace` promotes `starting → running` when it turns healthy. `Status` also notices crashes, hand-removed containers and containers started behind the backend's back, so the database follows Docker. **One operation per user at a time (in-process claim):** while a start or stop runs, `Status` only reports the row (an exited kept container is not a crash yet), a power-off during a start is refused with 409, and a second start just reports. A `starting` row *without* a container while nothing is running is the leftover of a backend that died mid-start: `Status`, `Start` and `Stop` reset it to `offline` (removing the half-made container and freeing its UDP block only when Docker confirms none is left). Rollback concludes "container gone" only on a real not-found, never because the daemon could not be asked; a leftover container with the workspace's name that the database does not record is replaced, not adopted (its password and ports are stale). An unhealthy *running* workspace stays `running` (the API reports `health: unhealthy`).

- Volume `berth-data-<username>` is mounted at `/home/user` and **never deleted in any state**. Registration only *records* its name; the volume is created idempotently on every start.
- All timeouts are env-configurable (defaults above).
- **Idle** (decision D2, implemented in M4) = a workspace that is up (`running`, or `starting` for good) has been **unused for `BERTH_IDLE_TIMEOUT` (default 30 min)**. "Used" = (a) a heartbeat: `last_active_at` is refreshed by `POST /api/workspace/heartbeat` and by Start; or (b) **busy**: for a `running` workspace, the average CPU between two looks of the reaper was at or above `BERTH_IDLE_CPU_PERCENT` (default 5, `docker stats` percent: 100 = one core). The backend cannot see the ttyd/neko WebSockets (they bypass it; it is deliberately not on the user networks), so the spec's "both sockets closed" is approximated by the heartbeat: the page sends it while it is open, which is exactly while its sockets are. Both conditions must be false for a stop, so background jobs are not killed; quiet jobs (waiting on I/O, `sleep`, an idle `tmux`) are *not* protected, and a stop ends every process (`docker stop`; files stay).
- Frontend calls `POST /api/workspace/heartbeat` every 30 s while the page is open and the workspace is starting/running, **visible tab or not** (an open page holds open sockets; M3 sent it only while visible), to refresh `last_active_at`. A hidden tab polls the status once a minute, so it learns that the workspace was powered off or that another account logged in and stops beating.

## Container spec

- Image `BERTH_WORKSPACE_IMAGE` (default `berth/workspace:latest`); name `berth-ws-<username>`; mount `berth-data-<username>:/home/user`.
- `--memory` / `--cpus` from the workspaces row; `--shm-size=2g` (Chromium); `--pids-limit 2048`; `--cap-drop NET_RAW`; `--security-opt no-new-privileges`; `--init`; stop timeout 15 s; no restart policy (the backend owns the lifecycle).
- **Networking (decision D1, implemented):** a workspace joins **only** its private network `berth-net-<username>`. The backend connects the Traefik container to that network (`BERTH_TRAEFIK_CONTAINER`) and labels the router `traefik.docker.network=berth-net-<username>`. The shared `berth-proxy` network holds only Traefik and the backend, so workspaces cannot reach each other or the backend. The reaper package's attach loop (`Manager.ReattachTraefik`) re-attaches Traefik to the networks of the workspaces that are `starting` or `running`, at startup and every `BERTH_PROXY_ATTACH_INTERVAL` (default 10 s; measured: workspaces were unreachable for 42 s after a Traefik recreation with a 60 s interval, 5 s with 10 s), because Docker drops attachments when the Traefik container is recreated.
- Env: neko screen/passwords/sub-path/WebRTC range (`internal/workspace/neko.go`). **neko v3 names** — the spec's `NEKO_EPR` is a v2 name (it still parses but logs "deprecated V2 configuration"): `NEKO_WEBRTC_EPR`, `NEKO_WEBRTC_NAT1TO1`, `NEKO_MEMBER_MULTIUSER_{USER,ADMIN}_PASSWORD` (defaults are `neko`/`admin`, so always set both), `NEKO_SERVER_PATH_PREFIX=/ws/<user>/browser` (neko 404s everywhere else; load the page **with the trailing slash**, its assets are relative), plus `NEKO_SERVER_PROXY=true`, `NEKO_SESSION_IMPLICIT_HOSTING=true` and `NEKO_SERVER_METRICS=false` (otherwise `<prefix>/metrics` answers for any logged-in user). The UDP block (`BERTH_UDP_PORTS_PER_WORKSPACE`, default **1**) is allocated at container creation inside an immediate transaction, recorded in the table, published port-for-port with `-p`, and released when the container is removed. **One port → `NEKO_WEBRTC_UDPMUX=<port>`** (neko multiplexes every viewer over it); a larger block → `NEKO_WEBRTC_EPR=<a>-<b>` (each viewer takes a port; closed tabs hold theirs for 5–10 s and sockets were seen to stay bound until neko restarted). A user's block is fixed when first allocated: changing the setting later only affects workspaces that have none.
- Traefik labels per user:
  - `<username>-term`: `PathPrefix("/ws/<username>/terminal")` → port 7681, StripPrefix middleware
  - `<username>-browser`: `PathPrefix("/ws/<username>/browser")` → port 8080 (not stripped: neko is told its own prefix)
  - Traefik is attached to each user network with **gateway priority -1**. Without it Docker makes the new network (`berth-net-<u>` sorts before `berth-proxy`) Traefik's default gateway and re-creates its published port: every in-flight connection through Traefik is reset, including the power-on request that triggered the attach (measured: 4 of 400 polled requests failed; with the priority, 0). The priority needs Docker Engine >= 28 (API 1.48): an older engine silently ignores it, so the backend logs an error at startup when it negotiates a lower API version.
  - both routers use the shared middleware `berth-auth@file` (`traefik/dynamic.yml`, so it exists even while the backend is down: a dead backend then yields a fail-closed 5xx instead of a 404). It is a Traefik `chain` of `berth-ws-headers` and then `berth-forward-auth` (the actual ForwardAuth), so a router names one thing and cannot have the check without the headers. A lowest-priority catch-all router for `/ws/` in the same file runs the same chain, so an anonymous caller gets 401 for *every* `/ws/...` path whether or not the user or container exists (otherwise Traefik's 404 reveals who has a workspace up) → `/api/auth/check`. **List it before StripPrefix** (`middlewares=berth-auth@file,<u>-term-strip`; browser router `berth-auth@file`): Traefik fills `X-Forwarded-Uri` from the URL at the moment ForwardAuth runs, so the other order shows the check a stripped path and every request gets 403 (measured with the real Traefik).
  - the response-header middleware `berth-ws-headers` (`traefik/dynamic.yml`) is the first member of the `berth-auth` chain, so every `/ws` route runs it: `X-Frame-Options: SAMEORIGIN`, `Content-Security-Policy: frame-ancestors 'self'`, and `Service-Worker-Allowed` deleted (an empty `customResponseHeaders` value removes a header). It replaces whatever the workspace sends, so a hostile workspace cannot loosen it. It sits on the response path only. It is listed **before** the check on purpose: a 401/403 that ForwardAuth writes itself never reaches a middleware listed after it (measured with the real Traefik), and headers first puts them on those responses too, with the backend's JSON body and `Cache-Control: no-store` unchanged. An earlier layout listed it as a second name in every router's `middlewares` label; that kept the 401/403 header-less and, worse, left workspaces created before the middleware existed without it (a container keeps its labels). In the chain the labels never change, so existing workspaces are protected as soon as Traefik reads the file.

## Backend API

```
M1  POST /api/auth/register     {username,password}
M1  POST /api/auth/login        {username,password} -> sets berth_session (Path=/api) and berth_ws (Path=/ws)
M1  POST /api/auth/logout
M1  GET  /api/auth/check        Traefik ForwardAuth: berth_ws cookie + username in path
M1  GET  /api/me                current user + workspace state (database only)
M1  GET  /healthz               liveness (compose healthcheck; not routed publicly)
M2  GET  /api/workspace         {username, workspace}: refreshed state, health, usage (docker stats), neko password while up
M2  POST /api/workspace/start | /stop   same body as GET (state after the call)
M2  POST /api/workspace/heartbeat       204
M5  GET  /api/admin/workspaces  admin only (first registered user)
```

The workspace endpoints answer `{"username": "<name>", "workspace": {...}}`. `username` is the account of the session cookie that made the request (never a request field), because the browser shares one cookie jar between tabs: a page that remembers who it believes is logged in compares the two and notices that another tab logged in as someone else. `/api/me` carries the user too; heartbeat has no body.

Errors are JSON `{"error": "..."}`. JSON bodies are required (`Content-Type: application/json`), size-capped, unknown fields rejected. **Every state-changing request must declare `Content-Type: application/json` — including the body-less ones (power on/off, heartbeat, logout)** — so a cross-site form cannot trigger them; after the login check, so strangers still get 401. Workspace errors never echo Docker internals (503 for no capacity or an unreachable daemon, 409 when a start or stop is in progress, otherwise a generic 500; details go to the log). `Deps.Workspaces == nil` means "no container backend": workspace endpoints answer 503 and accounts still work.

## Frontend pages

Served by the Go binary at `/` (same origin as `/api` and `/ws`); `web/README.md` has the module layout.

1. **Login / register** (register creates the account, then logs in).
2. **Workspace**: status bar (state, health, memory/CPU, Power off with an inline confirmation, Log out) and, depending on the state, a call to action ("Power on", with the note that data is kept), progress while `starting`, or — when `running` — a resizable split (mouse, touch, keyboard; ratio in localStorage; stacked under 900 px) of the xterm.js terminal and the neko iframe. The terminal is a ttyd client written for the ttyd protocol (`web/src/ttyd.ts`), not ttyd's own page: `/ws/<username>/terminal/ws`, subprotocol `tty`, binary frames, reconnect with backoff. The iframe is `/ws/<username>/browser/?usr=<user>&pwd=<neko_password>&embed=1`; `localStorage.neko_session` is cleared before it is created and on logout. Status is polled (2 s while starting, 10 s while running, once a minute in a hidden tab); heartbeat every 30 s while the workspace is starting/running, hidden tab included; any 401 returns to the login page.
3. **Admin** (M5): table of users + states with force-stop.

## Reaper

`internal/reaper`, one goroutine per loop, started from `cmd/berth` before the HTTP server and stopped (context cancelled, bounded wait of 8 s) before the database closes. **Sweep loop**, one `BERTH_REAPER_INTERVAL` (default 1 min) after the end of the previous pass and for the first time one interval after start: for every workspace that is not plain offline, at most 4 at a time, each with its own deadline and under a panic guard,

1. `Manager.Reconcile` = `Status` without the resource sample: the database follows Docker (a crashed container → `stopped` with its real finish time, a container removed by hand → `offline` and the UDP block released, a container started by hand → `starting` with a fresh idle clock);
2. `running`: read the container's cumulative CPU time (`Client.CPUUsage`, one cheap one-shot reading stamped with the daemon's clock) and compare with the previous pass: average ≥ threshold → **busy**, remembered in memory (not in the database: `last_active_at` stays "the user was here"), logged on change; the first look, a failed reading, or readings that cannot be compared (the counter restarted) give **no verdict and nobody is stopped on it** (a warning after 3 in a row, naming `BERTH_IDLE_CPU_PERCENT=0`). `running` or `starting`: if `now − max(last_active_at, floor, last busy) ≥ BERTH_IDLE_TIMEOUT` → `Manager.StopIfIdle` → `stopped` + `last_stopped_at`. `starting` is judged by its heartbeat alone (a container that never turns healthy leaves its row at `starting` for good; its CPU is not a user's job);
3. `stopped` for `BERTH_RECLAIM_AFTER` (default 7 days, counted from `last_stopped_at`): `Manager.ReclaimIf` → `docker rm` → `offline`, `container_id` cleared, UDP block released. The volume, the neko password and `last_stopped_at` stay; the next power-on creates a new container on the same volume;
4. containers carrying `berth.managed` that the database does not record are logged once (unknown user: left alone; known user: replaced at that user's next power-on). **Never removed**: labels are not proof of origin.

Rules that make it safe: the decision is made from a snapshot and **repeated by the Manager under the user's claim against the row as it is then** (a heartbeat, a power-off or a power-on in between wins; claim ops `opStop` for the idle stop, `opReclaim` for the removal; a user's Start during either gets 409, a Stop reports); `ReclaimIf` inspects the container first and never removes a running one or one that is not Berth's for this user (the wrapper's `RemoveContainer` is a force-remove that never takes volumes), applies the transition only to the container it removed (`OnlyIfContainer`), and releases the UDP block only if no container is left under the workspace's name; the **floor** is the process start, moved forward when the wall clock steps against the monotonic one (a resumed laptop): after a backend restart or a clock step nobody is stopped for one full idle timeout; Docker unreachable or timing out ends the pass (one log line per outage, keyed by failure class, not per workspace); shutdown cancels the Docker call in progress (every operation is crash-safe: the next `Reconcile` repairs the row).

**Attach loop** (`BERTH_PROXY_ATTACH_INTERVAL`, default 10 s, unchanged behaviour, now in this package): `Manager.ReattachTraefik` connects Traefik to the networks of `starting`/`running` workspaces only (a power-on attaches its own network before the container starts; walking every network that ever existed cost three daemon calls each, every 10 s, for ever). It is a separate loop on purpose: a slow sweep must not delay the 10 s that bounds the outage after a Traefik recreation (measured: 42 s with a 60 s interval, 5 s with 10 s), so "fold in" means the same package and shutdown, not the same tick.

Not done, on purpose: removing a user's network when the workspace goes offline (it would detach Traefik from, and delete, shared infrastructure; the `daemon.json` address pools are the sizing answer); counting ttyd/neko sockets (`docker exec ss`) or polling neko's stats API; touching `last_active_at` from the ForwardAuth check; a quota on data volumes (D7).

## Security decisions (keep these invariant)

- **Usernames** are used in container/volume/network names, Traefik router names and URL paths, so they are restricted to `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`, 3–32 chars (lowercase; no dots/underscores; no leading/trailing/double hyphen). Never relax this without auditing every place a username is interpolated. The manager re-validates before using one (`checkName`), and config values that reach Traefik label keys (entrypoint, container name) are validated at startup.
- **Passwords:** bcrypt (default cost 12, configurable 10–15), 8–72 bytes (bcrypt ignores bytes past 72). Login always spends one bcrypt compare — unknown user, bad format, or overlong password included — and returns one generic error, so neither response nor timing reveals which usernames exist.
- **Sessions: two cookies, two tokens (decision D4, implemented).** A login creates one session row with two independent 256-bit tokens, stored only as sha256: `berth_session` (`Path=/api`, the API credential) and `berth_ws` (`Path=/ws`, accepted *only* by the ForwardAuth check). Both are `HttpOnly`, `SameSite=Lax` (`Secure` when `BERTH_COOKIE_SECURE=true`). Traefik forwards the browser's cookies into the workspace container, where code running as the user can read them; because the API token is never sent under `/ws`, such code cannot *steal* it. That is weaker than "cannot call the API": a page served by a hostile workspace (it can replace ttyd/neko on their ports) shares the site's origin with `/api`, so its script can make the visitor's browser call the API as the visitor — own account in M2, admin endpoints in M5. Only serving `/ws` from a different origin closes it (decision D4c). Fixed TTL (`BERTH_SESSION_TTL`). Logout deletes the row (both tokens die), so the cookies are dead for every *new* request and WebSocket upgrade; **an already-open ttyd/neko stream is not terminated** (ForwardAuth runs once per request/upgrade).
- **ForwardAuth (`/api/auth/check`)** takes the original URI from `X-Forwarded-Uri` (Traefik sets it; keep `trustForwardHeader=false`) and accepts only `/ws/<user>/(terminal|browser)[/...]`: an encoded slash (`%2f`) is refused outright; the rest is percent-decoded and must have no empty, `.` or `..` segment, backslash or control character (so encoded backslashes and NULs are refused too). No/invalid session → 401; valid session for another user or any non-matching path → 403; a store error → 500. Fail closed. The endpoint is not routed publicly (hygiene — it only answers about the caller's own cookie).
- **Docker socket:** Traefik and the backend mount `/var/run/docker.sock` (read-only does not limit the API); both are root-equivalent on the host. The backend runs unprivileged and joins the socket's group (`DOCKER_GID`, required). Keep the backend's attack surface small; Berth only touches objects it labelled (`berth.managed`) and never removes volumes.
- **Web app headers** (every response from `internal/webui`): `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; frame-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, and `Permissions-Policy: clipboard-read=(), clipboard-write=(self), fullscreen=(self), autoplay=(self), camera=(), microphone=(), geolocation=(), payment=(), usb=()`. Scripts stay `'self'`-only (no inline script, no eval); styles allow `'unsafe-inline'` only because xterm.js creates `<style>` elements and style attributes (a strict `style-src` left the terminal unreadable; the page renders no server-supplied HTML, so there is no CSS-injection path). `connect-src 'self'` covers the same-origin terminal WebSocket in Chromium 141; older Firefox/Safari may need `'self' ws: wss:` (one constant in `internal/webui`). Clipboard-read is denied on purpose: with it neko copies the user's local clipboard into the workspace on every mouse-enter (after a prompt); Ctrl+V into the remote browser and copying out of it still work. The microphone is denied (neko's "share my microphone" button does not work). Only `/assets/*` (content-hashed by Vite) is cached as immutable. Responses under `/ws/` are not the SPA's: the `berth-ws-headers` middleware (the first member of the `berth-auth` chain in `traefik/dynamic.yml`) gives them `X-Frame-Options: SAMEORIGIN` and `Content-Security-Policy: frame-ancestors 'self'` (the SPA frames neko from the same origin; a page on any other origin, same-site or not, is refused) and removes `Service-Worker-Allowed`. They deliberately carry no other policy of the SPA's (neko and ttyd need their own scripts, styles and sockets).
- **Never pull or adopt blindly:** the API only creates containers from a local image. If a container named `berth-ws-<u>` exists but is not labelled as that user's, start refuses rather than adopting or removing it.
- Request IDs are server-generated; client `X-Request-Id` is ignored. Traefik drops header-alias spoofing (`aliasheadersstrategy=delete`).
- `BERTH_DEFAULT_CPUS` / `_MEM_MB` are finite and bounded; JSON responses are marshalled before the status line is written.

## Verified facts (against Traefik 3.7.16 + Docker 29.9, not assumptions)

- ForwardAuth is always a `GET` carrying only the headers in `authRequestHeaders` plus Traefik-set `X-Forwarded-{Method,Proto,Host,Uri,For}`; a client-sent `X-Forwarded-Uri` or `X_Forwarded_Uri` is overwritten/ignored. The check sees no `Upgrade`/`Origin`.
- Traefik withholds containers whose healthcheck is `starting`/unhealthy (they 404 until healthy) — the workspace `HEALTHCHECK` is the "container ready" signal for `starting → running`.
- Every container on a shared user-defined bridge can reach every other (name and IP). With per-user bridges, Docker's iptables isolation blocks cross-network traffic by IP too (tested). Default address pools allow only **~29 user networks** (`all predefined address pools have been fully subnetted`): set `default-address-pools` in `daemon.json` before onboarding users (README has the snippet).
- A container attached with `docker network connect` loses that attachment when it is recreated (e.g. Traefik after `docker compose up -d` with a new image), and its workspaces then 504. The backend's re-attach loop repairs this; the e2e run measures the recovery time.
- moby client: starting a running container and stopping a stopped one return "not modified", which the wrapper treats as success; the daemon normalises `NET_RAW` to `CAP_NET_RAW` when recording `CapDrop`; `ContainerStats` with a previous sample takes ~1 s.
- Workspace image (`images/workspace/README.md` has the evidence): every process runs as uid 1000 `user` (supervisord is root and drops privileges per program; never pass `--user`); the image `HEALTHCHECK` probes ttyd **and** neko under its prefix (neko's own `/health` check would report unhealthy under a prefix, so it is replaced); a killed ttyd/neko/Chromium is respawned in 1–3 s; `docker stop` takes ~1–2 s; files and the Chromium profile survive `docker rm`. Two things only broke on a real volume: neko seeds Chromium with session-only cookies (fixed by a managed policy), and a `docker kill` leaves `SingletonLock` pointing at the old hostname so Chromium refuses to open (the `berth-chromium` launcher removes it). The base image leaves `/var/log/neko` world-writable while supervisord (root) opens the log files, which let `user` make root create a file at an arbitrary path through a symlink — fixed in the Dockerfile, with a build-time assertion.
- ttyd runs with `--check-origin`: it refuses a WebSocket upgrade whose `Origin` differs from `Host`, **and one with no `Origin` at all**. neko does not check `Origin` (a valid token opens its WebSocket from anywhere), see D4b.
- Docker facts found while testing: a container's `State.Health` stays at its last value after it exits (ignore it unless running); a failed start of a kept container whose network was removed and recreated returns 404 (indistinguishable from "container gone" without a second inspect); the daemon returns 201 with *warnings* when the host cannot enforce a memory/PIDs limit (`... Limitation discarded.`) — the wrapper refuses such a container; `could not find an available, non-overlapping ... address pool` / `fully subnetted` means the address pools are exhausted (503); the daemon refuses `NanoCPUs` above the host's CPU count, so `BERTH_DEFAULT_CPUS` must not exceed it.
- Web app / Traefik (real Traefik 3.7.16, 85 probed paths): `berth-web` (compose labels, priority 1; rule excludes `/api`, `/healthz`, `/ws`), the `/ws/` fallback (file provider, priority 2) and per-user routers (priority = rule length, ≥ 29) are ordered explicitly. Traefik sanitises `//`, `.`/`..`, `%2e` and `%61` before routing and forwards the cleaned path to both the service and ForwardAuth; encoded slash, backslash, NUL and `%3b` get 400. `/api/auth/check` and `/healthz` stay unreachable through Traefik (their exclusion in the web rule is load-bearing: without it both answer). The web router has Traefik's `compress` middleware (the bundle is ~580 kB, 160 kB gzipped).
- ttyd starts one shell per WebSocket and ends it when the socket closes, so a page reload, a network blip or Reconnect gives a fresh shell and kills what ran in the old one (decision D12). The next two bullets cover when it ends too early (a dropped ping) and too late (an orphan bash).
- ttyd 1.7.7 **ignores the client's PAUSE**: with a raw client, PAUSE followed by `yes abc | head -c 6000000` delivered all 6 MB within 1 s, and RESUME changed nothing. It also **drops a client that does not answer its pings within 2x the ping interval** (10 s by default; seen in review with a CPU-throttled page: close code 1006 and `WS closed ... 10.00s` in `ttyd.log`, after which the SPA reconnects into a new shell). So the SPA cannot slow a flood of output, and the image runs ttyd with `--ping-interval 30` (a page that is busy for up to 60 s keeps its shell). The ttyd page must still keep up on its own (renderer choice, not flow control).
- Closing a terminal socket while bash sits at readline's `Display all N possibilities? (y or n)` prompt (two Tab presses at an empty prompt) leaves an **orphan `bash -l`** under ttyd: ttyd logs `killing process, pid: N` but never `process killed with signal 1`, because bash ignores SIGHUP there. It stays until the container stops (observed after 2.5 s and 5 min; every such reload adds one). Idle prompt, PAUSE-only, Ctrl-U and `echo hi` closes leave nothing. Not fixed; recorded under D12.
- `/ws` response headers (real Traefik 3.7.16 file provider, the real labels and `traefik/dynamic.yml`; `go test -tags integration -run Traefik ./internal/workspace` with `BERTH_TEST_TRAEFIK` pointing at the binary repeats the HTTP part): the headers middleware **replaces** a workspace's own `X-Frame-Options`/`Content-Security-Policy` (an upstream sending `ALLOWALL` and `frame-ancestors *` ends with exactly one of each, ours), deletes `Service-Worker-Allowed` when its configured value is empty, and does not touch the `101` of a WebSocket upgrade (not a document; the terminal socket works through auth, headers and strip). In headless Chromium 141: a same-origin page frames `/ws/<u>/browser/` and `/terminal/`; a page on another port of the same host (same site, other origin, the victim's cookies are sent) is refused with `an ancestor violates ... frame-ancestors 'self'` and the same page framed them with no middleware; the SPA is still unframeable (`DENY`, from any origin including its own); `navigator.serviceWorker.register(script, {scope: '/'})` from a `/ws/<u>/browser/` page fails with `SecurityError` (it registered when the upstream's `Service-Worker-Allowed: /` was passed through) while scope `/ws/<u>/browser/` still registers. The headers are the first member of the `berth-auth` chain, so ForwardAuth's own 401/403 carry them as well (the integration test asserts it on the real Traefik, and fails if the two chain members are swapped or the catch-all names `berth-forward-auth` directly).
- Rolling out a change to `traefik/dynamic.yml` (found while shipping the response headers): compose used to bind-mount the single file, so a tool or `git pull` that replaces it (new inode) left the running Traefik on the old content (measured on the shared test stack: the container's inode differed from the host's and `grep berth-ws-headers` inside the container found nothing) and `docker compose up -d` did not recreate Traefik while its own service spec was unchanged. Compose now mounts the `./traefik` **directory** at `/etc/traefik/dynamic` and starts Traefik with `--providers.file.directory`, which Traefik watches, so a replaced file is picked up. The first upgrade changes Traefik's spec, so `docker compose up -d` recreates it by itself (the re-attach loop restores the user networks within `BERTH_PROXY_ATTACH_INTERVAL`). Every `*.yml` in `traefik/` is loaded: keep other files out. Labels are different: **a container keeps the labels it was created with**, so a label change reaches an existing workspace only when its container is recreated (`docker rm -f berth-ws-<user>` by hand: the next Status shows `offline`, the next power-on recreates it with the same neko password and the same data volume, and a UDP block allocated again; a kept container is never replaced just because its labels are old). That is why behaviour that must reach every workspace lives in `dynamic.yml`, behind the one `berth-auth@file` name.
- `Range` and Traefik's `compress`: `http.ServeContent` honours `Range`, and the `compress` middleware on the web router then encoded the 206 body itself (`206`, `Content-Encoding: br` or `zstd`, `Content-Range: bytes 0-9999/580030`, an identity-based range on an encoded body; gzip requests were left uncompressed). A client that decodes first gets the right bytes (checked), one that applies the range to the encoded representation does not; either way the response contradicts itself. `internal/webui` deletes `Range` and `If-Range` before `ServeContent` and sends `Accept-Ranges: none`: every request for a file is a 200 or a 304 (`If-None-Match` wins over a `Range`), compressed or not (verified through `compress`, old handler vs new).
- neko in the browser (headless Chromium 141 through Traefik and the SPA): the iframe loads same-origin (neko sends no `X-Frame-Options`/CSP), `?usr=&pwd=` auto-login works and neko removes both from its address (`location.search` is `?embed=1` afterwards; the iframe's `src` attribute still holds the password), WebRTC connects in 1–2 s (VP8 1280x720), mouse/keyboard/clipboard work, `embed=1` hides neko's chrome but keeps Fullscreen and Picture-in-Picture. neko keeps its session token in `localStorage.neko_session` on the Berth origin; a reused token makes a second tab take over the first and (observed with a port range) can leak a UDP socket, so the SPA clears it before the frame loads and on logout. neko does not check `Origin` on its WebSocket; Traefik's ForwardAuth does require `berth_ws`. Logging out does not stop an open stream (already documented), but after the signalling socket drops neko shows "session expired".
- WebRTC needs `BERTH_PUBLIC_IP` for every browser that is not on the Docker host (measured with a client in another network namespace: connects through the published port with `NEKO_WEBRTC_NAT1TO1` set, never connects without it; on the host itself it works either way because the host routes to the bridge). With it empty neko also calls `checkip.amazonaws.com` at every start. The browser sends only an mDNS host candidate; neko cannot resolve it and connects through a peer-reflexive pair.
- Reaper on the real stack (Docker 29.9, vfs, Traefik 3.7.16, the real workspace image; `BERTH_IDLE_TIMEOUT=1m BERTH_RECLAIM_AFTER=1m BERTH_REAPER_INTERVAL=10s`, state read from a copy of the SQLite file so that no API call reconciles for it; `scripts/e2e-reaper.sh`, 43 checks, run three times: all passed): heartbeats every 15 s for 140 s keep it running; with the heartbeats stopped it is stopped **about 60 s after the last one** (47-54 s into the wait, which began up to 15 s after it; log `idle_for=1m0s` to `1m9s`) and the container is kept `exited` with `last_stopped_at` set; stopped for the reclaim age it is **removed 52-64 s after the stop was seen** (the age plus up to one interval): the container is gone, `docker volume ls` still lists `berth-data-alice`, `container_id` and the UDP block are NULL, the neko password stays, the user network `berth-net-alice` stays; the next power-on creates a new container (different ID) on the same volume, the file written before is there, the password is unchanged, port 30000 is allocated again. A `nohup setsid yes` job (99.8-100.2% of a core) kept it running for 150 s with no heartbeat at all (`last_active_at` untouched, one `workspace is busy` log line) and it was stopped 66-70 s after `pkill yes`. `docker kill` of the container was recorded as `stopped` within 2-4 s and `docker rm -f` as `offline` (UDP block released) within 4-6 s, by the reaper alone. With the backend down for 80 s (last activity 85-86 s old at the restart) the workspace was still running 35 s after the restart and stopped 57-58 s after it. `docker stop` of the backend took under a second and logged a clean shutdown. In headless Chromium (`web/e2e/reaper.mjs`, 9 checks): a visible tab and a hidden one (faked `visibilityState`) each kept the workspace up for 150 s; closing the tab stopped it 71 s later; a page that stayed open with its heartbeats blocked and its neko viewer gone was powered off 63 s later, noticed at its next poll (panes gone, "Your workspace is powered off ... Programs that were running in it ended with it. Your files are kept"), and Power on brought the terminal back with the file written earlier.
- CPU as the reaper sees it: an unattended workspace of the real image averages **0.86% of one core** over three minutes, measured twice (from 90 s after power-on, and from 20 s after a viewer had left), about a sixth of the 5% threshold; with a viewer attached (the terminal plus neko streaming video at 1280x720@30) it averaged **35%** of a core over 90 s, so a connected viewer counts as use by itself (a page whose heartbeats fail but whose video still flows is not stopped). The `Stats` sample behind `GET /api/workspace` (`IncludePreviousSample`) costs the daemon a second; the image's healthcheck (two `wget`, every 5 s) makes a one-second window read 0.04-0.3% and, once in seven samples, 4.19%, which is why the reaper compares two cumulative readings of the container's cgroup (`Client.CPUUsage`: `stream=false&one-shot=true`, answered at once, stamped with the daemon's clock) over the whole interval between two passes instead of sampling. A job started with `nohup setsid ... &` and a terminal that closes at once can be killed before `setsid` has detached it (it survived in one run and not in another): give it a moment, as ttyd ends the shell's whole process group when the socket closes (D12).
- A backend container that is unhealthy/restarting does not take workspace routes down: the middleware lives in the file provider, so ForwardAuth fails with a 500 instead of a 404.

## Deviations from the spec (confirm at milestone review)

**M4:** the heartbeat is sent from a **hidden tab too** (reverses M3) and a hidden tab polls once a minute; **idle stop also applies to `starting`** (heartbeat only: a start that never turns healthy leaves its row there for good); CPU load counts as use **only for `running`**, as an **average between two passes** (cumulative reading, kept in the reaper's memory, not written to `last_active_at`), not the spec's one-second sample; **no ForwardAuth touch**; **no network removal** (an offline user keeps an empty `berth-net-<user>`; a stopped workspace keeps its UDP port until reclaim); **unrecorded containers are logged, never removed**; the Traefik re-attach is **in the reaper package but a loop of its own** (not the one-minute tick: 5 s vs 42 s outage after a Traefik recreation) and only for `starting`/`running` workspaces; `Reconcile` is `Status` without the resource sample, and the reaper also promotes `starting → running` (readiness no longer needs someone to poll); `store.Store.ListWorkspaces` leaves secrets empty; new `docker.Client` methods `CPUUsage` and `ManagedContainers` (still no volume or network removal); new env vars `BERTH_IDLE_TIMEOUT`, `BERTH_RECLAIM_AFTER`, `BERTH_REAPER_INTERVAL`, `BERTH_IDLE_CPU_PERCENT` (bounds: 1m-3650d, 1m-3650d, 5s-1h, 0-1000; 0 ignores CPU).

**M3:** the built frontend is **embedded in the backend binary and served by it** (`internal/webui`) instead of a separate frontend container; style CSP allows `'unsafe-inline'` (see Security); the default is **one multiplexed UDP port per workspace** (`NEKO_WEBRTC_UDPMUX`), not a block of 8; `BERTH_PUBLIC_IP` is mandatory in practice for remote browsers; the neko iframe uses `embed=1` and the member password in the URL; `BERTH_PROXY_ATTACH_INTERVAL` is a new setting; the workspace endpoints answer `{username, workspace}` instead of `{workspace}`; `berth-auth@file` is now a chain of the `berth-ws-headers` response headers (framing and service-worker policy) and the ForwardAuth check, and compose mounts the `traefik/` directory instead of one file; `internal/webui` never answers a range request.

**M1/M2:** `users.is_admin` column (needed for "first user is admin"); `sessions` table (server-side sessions so logout truly revokes) with **two tokens per login** (`berth_session`/`berth_ws`); `workspaces.volume_name UNIQUE` and CHECK constraints; extra package `internal/config`; `GET /healthz`; `/api/auth/check` returns **401** (no session) vs **403** (wrong user) where the spec says "otherwise 403"; register returns `{user, workspace}` and does not log in; Go floor 1.24 and the **moby client** instead of `github.com/docker/docker/client`; hardening flags on Traefik (`encodedcharacters.*`, `aliasheadersstrategy`, ForwardAuth `maxResponseBodySize`); the ForwardAuth middleware lives in `traefik/dynamic.yml`; the backend image is `berth-backend:local`; the **data volume is created at first start**, not at registration; workspaces join **only** their private network (not the shared `berth-proxy`); the backend needs `DOCKER_GID`; UDP block allocated at container creation and released at removal; extra container hardening (`--pids-limit`, `--cap-drop NET_RAW`, `no-new-privileges`, `--init`).

## Open decisions (resolve with the user before/in the named milestone)

- **D2 (M4, implemented on the proposed defaults; awaiting confirmation) Idle signal.** The backend never sees WebSocket open/close. Implemented: heartbeat from an open page (visible or hidden: this reverses M3, which beat only while visible), plus average CPU ≥ 5% between reaper passes for running workspaces. Left out after review: touching `last_active_at` from the ForwardAuth check (it runs once per request or upgrade, so it only records the moment a socket opens, and it would put a database write in the fail-closed auth path), neko's stats API (the backend is not on the user networks), counting established connections to ttyd/neko with `docker exec` (the one signal that would make "sockets open = in use" literally true, including for someone using `/ws/<u>/terminal/` without the SPA; about 80 lines; say if you want it). Consequence to accept: a forgotten open tab keeps its workspace up for ever; a quiet job in a closed tab is stopped.
- **D3 (M5) Admin bootstrap.** "First registered user is admin" is a takeover window on a fresh public deploy, and a DB reset (`docker compose down -v`) re-opens it while `berth-data-*` volumes survive (a new registrant of a surviving name inherits its files). Proposed: optional `BERTH_ADMIN_USERNAME`/bootstrap token, `berth admin promote`, and a volume owner label.
- **D4c (M3/M5) Origin isolation of workspaces.** Same-origin workspace pages can call the API as the visitor (see Sessions above); path-scoped cookies, `Origin` checks and CSRF tokens cannot stop script that runs on the Berth origin. The fix is a separate origin for `/ws` (e.g. `ws.<domain>`, `berth_ws` scoped to that host, `berth_session` never sent there), which needs host-based routing and a wildcard name/certificate — a deployment decision. Until then treat anything a workspace serves as same-origin script; the neko iframe added in M3 makes it reachable (the SPA frames `/ws/<user>/browser/` on the same origin). Two vectors this entry used to leave open are now closed at the edge, neither of which needs a separate origin: **framing** (a page on a sibling origin of the same site framed the victim's live shell or remote browser with the victim's cookies and received their keystrokes; `SameSite=Lax` does not stop same-site pages) is refused by `X-Frame-Options: SAMEORIGIN` and `frame-ancestors 'self'` on every `/ws` response, and the SPA stays unframeable; **service workers** (a workspace page sending `Service-Worker-Allowed: /` could register a worker with scope `/`, which then sits in front of the login page and the app bundle, outlives logout, power-off, container removal and the session, and applies to every account later used in that browser profile) are limited by deleting that header, so a worker's scope ends at its script's directory under `/ws/<user>/<section>/`, a path only that user's session reaches. What remains: script served from `/ws` still runs on the Berth origin (the API-as-the-visitor call above, and a worker for its own path), and logout does not clear storage (`Clear-Site-Data: "storage"` from `POST /api/auth/logout` would; not done, and it would also drop the SPA's own `localStorage` layout preference).
- **D4b (M3) WebSocket `Origin`.** The check never sees `Origin`; same-site/different-origin pages could open a workspace WebSocket with the victim's `berth_ws` cookie. ttyd already runs with `--check-origin` (verified); neko does not check `Origin` at all (verified), so M3 must either pass `Origin` to the check or rely on neko's token being unguessable.
- **D6 (M3, mostly verified) neko WebRTC.** Verified in a real browser: video, input, clipboard, multiplexed UDP port, behaviour with and without `BERTH_PUBLIC_IP` (see Verified facts). Not verified: a real NAT or cloud firewall, IPv6, `userland-proxy=false` at scale, TURN, audio, Firefox/Safari. neko contacts Google's STUN server by default (leaks the visitor's address and is useless once `BERTH_PUBLIC_IP` is set); replacing it needs a non-empty `NEKO_WEBRTC_ICESERVERS_*` list and is untested.
- **D12 (M3) Terminal sessions.** (M4: tmux would make a reload or a closed tab lossless for as long as the container lives, i.e. up to the idle timeout; it would not survive an idle stop.) Each terminal connection is a new shell; a reload or a network blip kills running jobs. `tmux new-session -A -s main` as ttyd's command (tmux is in the image) would make the session survive, at the price of tmux's own scrollback/prefix key. Not done; needs a decision. A related leak (Verified facts): a socket closed while bash waits at readline's `Display all N possibilities?` prompt leaves a `bash -l` that ignores SIGHUP until the container stops. `ttyd --signal 9` (untried) might end it, but a stronger signal could also take down nohup'd or backgrounded jobs that survive a reload today; tmux as ttyd's command would make both questions moot.
- **D11 (M2, unverified) Image provenance.** `BASE` defaults to `ghcr.io/m1k1o/neko/chromium:3.2.0` (tag exists, multi-arch, checked by registry metadata). In the sandbox ghcr layers and the Debian mirrors are unreachable, so the image was built and tested on the Docker Hub `m1k1o/neko:chromium` base with the static ttyd 1.7.7 binary instead of apt: the apt step and a build on the pinned ghcr tag have never run. The Dockerfile asserts the exact neko config lines it patches, so a mismatch fails the build rather than the container.
- **D13 (M4) What a stop costs, and what it does not protect.** `docker stop` ends every process in the workspace, including `nohup`/`tmux` jobs that are quiet (waiting on I/O, `sleep`, an editor with unsaved buffers); only CPU load (>= 5% of a core on average) and an open page protect a workspace, and a forgotten open tab protects it for ever. Options if that is wrong: a longer `BERTH_IDLE_TIMEOUT`, counting established connections to ttyd/neko with `docker exec` (D2), a maximum uptime, or `BERTH_IDLE_CPU_PERCENT` lower/higher. The page tells the user that programs ended and files are kept.
- **D14 (M4) Capacity after the reaper.** Reclaim frees a container (memory, disk of its writable layer) but nothing else: a stopped workspace keeps its UDP port until reclaim, an offline user keeps an empty Docker network and an attachment-free place in the address pools, and **data volumes are never removed**, so abandoned accounts accumulate (no quota: D7). Pruning empty networks of offline users is possible (detach Traefik, remove, under the user's claim, with a burst test of the connections through Traefik) but was left out of M4 because it touches shared infrastructure; the `daemon.json` address pools are the sizing answer.
- **D7 (M5) More hardening.** seccomp profile for Chromium instead of broader caps, disk quota for `berth-data-*` (and keep `berth-state` off that disk), `--shm-size` ≤ half of memory (spec says 2g; with the default 2 GiB limit a full `/dev/shm` can OOM the container).
- **D10 (M5) Login rate limiting** (deliberately deferred), open registration, and a cap on concurrent `docker stats` calls, and clamping a stored `cpu_limit` to the host's CPU count at create time (each `GET /api/workspace` on a running workspace costs ~1 s of daemon time).
